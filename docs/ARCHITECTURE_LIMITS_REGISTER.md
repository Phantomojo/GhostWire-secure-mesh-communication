# GhostWire Architectural Limits and Decision Register

**Status:** Living engineering register.
**Use:** Record verified architectural limits as they are discovered, make the immediate containment explicit, and preserve the recommended long-term design and acceptance criteria.
**Rule:** A limitation is not closed because it has been documented. It is closed only when its acceptance tests pass in the supported build matrix.

## Decision method

Each entry separates the observation from the recommendation. “Containment” prevents overclaiming or unsafe deployment now. “Long-term decision” describes the architecture to build when the dependency work is ready. Priority measures impact on privacy, security, correctness, and production claims; it is not a measure of developer effort.

| Status | Meaning |
|---|---|
| **Open** | Verified limitation with no implemented containment. |
| **Contained** | Immediate mitigation exists, but the long-term design is not delivered. |
| **In progress** | Implementation/test work is actively underway. |
| **Supported** | Long-term design is implemented and passes stated acceptance checks. |
| **Rejected** | Deliberately outside GhostWire’s supported architecture. |

## Newly discovered issues workflow

When a test or review surfaces a new limit, add a row before treating it as “fixed.” The entry must cite the source/test command or trace, state whether it blocks a public claim, name a stable owner/module, and specify an executable acceptance condition. If an issue cannot be reproduced, label it **unconfirmed** rather than escalating a hypothesis into architecture.

## Current long-term direction

GhostWire should evolve around a small number of policy-authoritative boundaries: a `CommandService` for all clients, a `TransportCoordinator` for outbound delivery, a shared `IngressValidator` for inbound traffic, a durable lifecycle store, and a privacy-safe public fault layer. Mesh/libp2p remains a control/group-dissemination plane; direct, anonymous, offline, and bulk delivery become explicit capability-classed adapters. This design prevents a carrier’s convenience behavior from silently redefining user privacy or delivery semantics.
